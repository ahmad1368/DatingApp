قوانین صرفه‌جویی توکن (این بخش بر همه‌چیز حاکمه)
خروجی چت مینیمال: بدون narration مرحله‌به‌مرحله، بدون تکرار این قوانین در پاسخ. فقط پیام‌های کوتاه ۱ خطی در نقاط کلیدی + خلاصه پایانی.

برای انتخاب ایشیو فقط از `gh issue list`/`gh pr list` استفاده کن (متن ساده)؛ مرورگر یا اسکرین‌شات اصلاً لازم نیست، این پایپلاین QA بصری نداره.
Subagent فقط اگر واقعاً کار مستقل و موازی‌پذیر باشه؛ برای این پایپلاین معمولاً لازم نیست.

QA بصری (اجرای شبیه‌ساز، اسکرین‌شات، تست دستی UI) در این پایپلاین انجام نده.
تحلیل «چرا این ایشیو» رو فقط ۲-۳ خط در بدنه PR بنویس، نه به‌صورت مکالمه‌ی مفصل در چت.
دستورات git/gh مرتبط رو تا حد امکان در یک فراخوانی ترمینال بچین (مثلاً add+commit پشت‌سرهم) به‌جای چند تول‌کال جدا.
مراحل
آماده‌سازی: `git status` تمیز باشه → `git checkout stage` → `git pull origin stage` (برنچ پایه‌ی همه‌چیز `stage` است).
کش انتخاب ایشیو (جلوگیری از هزینه‌ی تکراری): فایل `.claude/next-issue-cache.json` رو چک کن.
اول یک fingerprint سبک بگیر (فقط شماره/تاریخ/عنوان، نه بدنه/کامنت):
`gh issue list --repo ahmad1368/DatingApp --state open --json number,updatedAt,title`
اگر کش وجود داره، `queue` توش خالی نیست، و آرایه‌ی `snapshot` توش دقیقاً با fingerprint فعلی یکیه (همون شماره‌ها + همون updatedAt) و آرگومان `--refresh` هم داده نشده → تحلیل کامل رو رد کن، مستقیم برو مرحله ۳ و اولین آیتم `queue` رو بردار.
در غیر این صورت (کش نیست/خالیه، fingerprint فرق کرده، یا `--refresh` داده شده) → مرحله ۲ (تحلیل کامل) رو اجرا کن و کش رو با ساختار زیر بازنویسی کن:
```json
     {
       "generated_at": "<ISO time>",
       "snapshot": [{"number":12,"updatedAt":"...","title":"..."}],
       "queue": [{"number":12,"reason":"..."},{"number":7,"reason":"..."}]
     }
     ```
تحلیل کامل (فقط وقتی کش نامعتبره): بدنه/لیبل/کامنت تمام ایشیوهای باز رو بخون، `gh pr list --base stage --state all` رو هم ببین تا چیزهایی که قبلاً پیاده‌سازی/در دست PR هستن رو کنار بذاری، بر اساس وابستگی منطقی (نه شماره/تاریخ) کل صف اولویت رو بساز و در `queue` کش ذخیره کن.
انتخاب ایشیو: اولین آیتم `queue` (از کش تازه یا معتبر) رو برای این اجرا بردار. بلافاصله همون آیتم رو از آرایه‌ی `queue` در فایل کش حذف و فایل رو ذخیره کن (تا اجرای بعدی سراغش نره، حتی اگه هنوز روی گیت‌هاب به‌خاطر merge‌نشدنِ PR باز باشه). یک جمله دلیل انتخاب کافیه.
برنچ: `issue-<شماره>-<slug-انگلیسی>` از `stage` (نه از main).
پیاده‌سازی:
الزامات معماری و استانداردهای کدنویسی پروژه را رعایت کن.
قبل از ادیت هر فایل موجود، حتماً یک‌بار با Read بخونش؛ کد حدسی روی فایل ندیده ممنوع.
تست: فایل Unit test یا integration test مربوط به تغییرات رو بنویس (بدون نیاز به اجرای سوئیت سنگین).
بررسی نهایی: بررسی سریع syntax و صحت کد انجام بده.
کامیت/پوش/PR: کامیت انگلیسی → push → `gh pr create --base stage` (فقط به `stage`؛ بدون merge خودکار) → روی همون PR ریپورت انگلیسی کوتاه بنویس:
```
   ## Summary
   - Why this issue now (1-3 lines)
   - What changed (files, paths)
   - Tests added
   ## Notes
   ```
پایان: بعد از باز شدن PR متوقف شو. خروجی نهایی چت: فقط شماره ایشیو، نام برنچ، لینک PR.
